# OXIA Subscription Setup

Premium is sold **only** through the native stores (Google Play Billing on
Android, StoreKit on iOS). There is no card processor in the app.

| Product | Product ID | Price |
| --- | --- | --- |
| Monthly | `oxia_premium_monthly` | €2.99 / month |
| Yearly | `oxia_premium_yearly` | €26.99 / year (25% off) |

Trial: 7 days, configured **in the store consoles** (not in code).

## 1. Secrets

| Secret | Used by | Required for |
| --- | --- | --- |
| `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` | `verify-purchase`, `subscription-webhook` | Android receipt validation + RTDN state lookup |
| `APPLE_SHARED_SECRET` | `verify-purchase` | iOS receipt validation |
| `SUBSCRIPTION_WEBHOOK_SECRET` | `subscription-webhook` | Authenticating provider callbacks |

Until `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` / `APPLE_SHARED_SECRET` are set, the
matching platform's verification returns "Purchase verification failed" and
logs `... not configured` in the Edge Function logs. This is intentional
fail-closed behaviour — never grant premium without a validated receipt.

### GOOGLE_PLAY_SERVICE_ACCOUNT_JSON

The full JSON key file of a Google Cloud service account with Play Developer
API access. Paste the file contents verbatim (including newlines in
`private_key`).

1. Google Play Console → **Setup → API access**.
2. Link (or create) a Google Cloud project.
3. Under **Service accounts** → *Create new service account* → opens Google
   Cloud IAM.
4. Create the service account, then **Keys → Add key → Create new key →
   JSON**. Download it.
5. Back in Play Console → **API access → Grant access** for that service
   account with permissions:
   - *View financial data, orders, and cancellation survey responses*
   - *Manage orders and subscriptions*
6. Enable the **Google Play Android Developer API** in the Cloud project.
7. Save the downloaded JSON as the secret value.

Propagation can take up to 24 h after granting access.

### APPLE_SHARED_SECRET

The App-Specific Shared Secret used by `/verifyReceipt`.

1. App Store Connect → **Users and Access → Integrations → In-App Purchase**.
2. *App-Specific Shared Secret* → **Generate** (or use the existing one).
3. Copy the 32-character hex value into the secret.

Rotating it invalidates the old value — update the secret at the same time.

### SUBSCRIPTION_WEBHOOK_SECRET

Random value generated by Lovable. It is appended as `?token=` to the webhook
URL given to both providers. Rotating it requires updating the URL in both
consoles.

## 2. Store console products

Create the two subscription products with **exactly** the product IDs above,
in the same base plan/subscription group, with a 7-day free trial offer.

- Google Play Console → **Monetise → Subscriptions**.
- App Store Connect → **Subscriptions** (one group, two durations).

iOS additionally needs the **In-App Purchase** capability enabled in Xcode.

## 3. Webhooks (keeps `profiles` in sync)

Edge Function: `supabase/functions/subscription-webhook/index.ts`
(deployed with `verify_jwt = false`; authenticated by the `token` query param).

```
https://phhyfmztzgkorxhasyaw.supabase.co/functions/v1/subscription-webhook?token=<SUBSCRIPTION_WEBHOOK_SECRET>
```

### Google Play — Real-time Developer Notifications (RTDN)

1. Google Cloud → **Pub/Sub → Create topic**, e.g. `oxia-rtdn`.
2. Grant `google-play-developer-notifications@system.gserviceaccount.com` the
   **Pub/Sub Publisher** role on the topic.
3. Create a **push subscription** on that topic with the endpoint URL above.
4. Play Console → **Monetise → Monetisation setup → Real-time developer
   notifications** → paste the topic name and *Send test notification*.

Handled notification types: purchased (4), renewed (2), recovered (1),
restarted (7) → active; cancelled (3), on hold (5), paused (10), revoked (12),
expired (13) and voided purchases → inactive. For every subscription event the
function re-reads the authoritative expiry from the Play Developer API instead
of trusting the event payload.

### Apple — App Store Server Notifications V2

1. App Store Connect → your app → **App Information → App Store Server
   Notifications**.
2. Set both **Production** and **Sandbox** URLs to the endpoint above
   (Version 2).
3. Send a test notification.

Handled: `DID_RENEW`, `SUBSCRIBED`, `DID_CHANGE_RENEWAL_STATUS`,
`DID_FAIL_TO_RENEW` (grace period stays active until expiry),
`EXPIRED` / `REVOKE` / `REFUND` / `GRACE_PERIOD_EXPIRED` → inactive.

## 4. How state is stored

- `subscription_receipts` (server-only, no client access) links a store
  purchase to a user: `purchase_token` (Android) or `original_transaction_id`
  (iOS), plus product, plan, expiry, active flag and last event.
  `verify-purchase` writes this row; `subscription-webhook` looks the user up
  through it.
- `profiles.is_subscribed`, `profiles.subscription_expires_at`,
  `profiles.subscription_plan` are the fields the app reads. They are
  writable **only** by the service role — the `protect_subscription_fields`
  trigger reverts any client-side change.
- `public.is_premium(uuid)` is the single source of truth in RLS policies and
  is mirrored client-side by `usePremiumStatus`.

If a webhook arrives before the client finished verifying (no matching
receipt), the event is logged and ignored; the next renewal event or a
`restorePurchases()` call reconciles it.

## 5. Testing checklist

- [ ] Play Console test notification returns 200 in the function logs.
- [ ] App Store sandbox notification returns 200.
- [ ] License-tester purchase on Android flips `profiles.is_subscribed`.
- [ ] Sandbox purchase on iOS flips `profiles.is_subscribed`.
- [ ] Cancelling in the store eventually flips it back to `false` at expiry.
- [ ] A free account sees blurred premium cards with the upgrade CTA.
